# 0010: Retry Marketplace Clones Over SSH

## Summary

Let `tx marketplace add` reach a private repository. An HTTP(S) source is still attempted over HTTP(S) first, exactly as it is today; when that clone fails, the addition derives the SSH source from it and retries the clone once. A user with an SSH key and no HTTPS credential — the ordinary case on a developer machine and in CI — installs a private marketplace without typing a different URL.

**Spec:** [Plugin System](../specs/plugin-system/)
**Status:** complete
**Depends On:** 0008

## Motivation

`tx marketplace add fx/private-plugins` expands to `https://github.com/fx/private-plugins.git` and hands it to `git clone`. For a public repository that is the right default and nothing here changes it. For a private one it fails, and it fails on exactly the machines that can already reach the repository: a developer whose SSH key is loaded in their agent, a CI job with a deploy key, a workstation whose Git is configured for SSH against an internal forge. Those setups authenticate `git@github.com:fx/private-plugins.git` without a prompt. HTTPS is the one transport they are not set up for.

[Change 0002](./0002-add-plugin-marketplaces.md) recorded the assumption behind the current behavior when it chose cloning over a catalog: "Existing Git/SSH access already handles the private-repository use case." That is true of Git and untrue of `tx`, because `tx` never offers Git the SSH source. Shorthand expansion produces HTTPS unconditionally, so the SSH access the user already has is unreachable through the shorthand the manual advertises. This change supersedes that assumption rather than contradicting it: SSH access does handle the case, once the addition actually tries it.

The workaround today is to type the SSH URL. It works, and it is worth stating why it is not enough. It costs the user the shorthand, so `owner/repository` becomes a form that works for public repositories and silently does not for private ones — a distinction the user learns from a clone failure. And it is not a failure the user can act on from the message: `git clone` over HTTPS against a private repository reports a credential problem, not "you have SSH access to this and I did not use it."

The SSH source is derivable from the HTTPS one. The host and the path are both present, and the SSH login of every forge that matters is `git`; only the transport differs. So the fallback needs no new input from the user, no configuration, and no stored credential — it re-spells a source it already has.

One thing has to change for the retry to be reachable at all. `git clone` over HTTPS against a private repository does not fail when no credential is configured; it prompts on the terminal and waits. A blocking prompt means the SSH attempt never runs, and the user is left answering a question about a transport they were not trying to use. Clone attempts therefore run with Git's own terminal prompt disabled, so a missing credential is a fast failure rather than a prompt.

### Functional Requirements

[Plugin System: Marketplace Plugin Ownership](../specs/plugin-system/index.md#marketplace-plugin-ownership) owns the transport sequence, SSH derivation, non-interactive execution, staging per attempt, and combined failure reporting. Its scenarios are this change's acceptance criteria and are not restated here. [Plugin System: Local Marketplace Sources](../specs/plugin-system/index.md#local-marketplace-sources) is unaffected: classification decides between a local reference and Git before any transport question arises, and a local source never reaches a clone.

What implementing them requires of this change:

- **Clone attempts stop prompting on the terminal.** This is a deliberate behavior change, and it is what makes the fallback reachable. A private HTTPS clone with no configured credential today blocks on Git's built-in `/dev/tty` prompt; after this change it fails, and the SSH retry runs. Configured credential helpers, `GIT_ASKPASS`, and token-bearing URLs are untouched — only Git's own terminal prompt is suppressed, and only for clone attempts. `marketplace list` and dependency installation keep the environment they have today.
- **The retry covers the clone and nothing else.** Manifest validation, dependency installation, and the duplicate-name check run after a clone succeeds, and a failure in any of them MUST NOT trigger an SSH attempt. Retrying them would re-run a trusted lifecycle script against a second checkout of the same commit.
- **Each attempt needs its own staging directory.** `git clone` refuses a destination that is not empty, and a failed clone can leave a partial one behind. Reusing the first attempt's staging directory would make the SSH attempt fail for a reason unrelated to SSH. Every staging directory the addition creates MUST still be removed on every exit path, so a failed retry leaves marketplace storage exactly as it found it — but a removal the filesystem refuses MUST NOT become the reported failure, whether that failure is a clone error between attempts or a publication error after the last one, and MUST NOT cancel a remaining attempt, because that would lose the error and the installation while leaving the directory behind anyway.
- **A source's credentials MUST NOT reach the combined failure, anywhere in it.** `https://<token>@github.com/owner/repository.git` is a supported source, and naming the attempted sources in the failure is new behavior, so without redaction this change would newly print a token to standard error. The redaction binds the whole combined failure: the attempted sources it names, the Git output quoted between them — Git repeats the clone URL in its stderr, spelling the credential as a `userinfo@host` run in each of the forms it prints — and the underlying failures attached as its cause. It removes the password and every `userinfo@` run Git quotes; a userinfo *user* spelled without its `@`, such as a server message naming the account, MAY remain, because deleting a bare identifier corrupts the message around it. The derived SSH source carries no credential to begin with, and a lone failure is reported exactly as Git reported it.
- The marketplace plugin owns all of this. No requirement here may add transport, URL, or Git vocabulary to any module under `src/`, and `test/plugin-boundary.test.ts` MUST keep passing unmodified.

## Design

### Approach

Everything lands in `plugins/marketplace/manager.ts`, in the clone path only.

`normalizeMarketplaceRepository` keeps its job unchanged: it expands `owner/repository` shorthand to an HTTPS clone source and passes everything else through. A new derivation reads that normalized source and produces the SSH source for it, or nothing when the source is not HTTP(S). So the transport sequence is decided from one place, after shorthand expansion, and an explicitly typed `https://` URL gets the same treatment as a shorthand that expanded into one.

The clone becomes a bounded loop over one or two candidate sources rather than a single call. Each iteration creates its own staging directory, clones into it, and returns it on success; on failure it records the error, removes the staging directory, and lets the next candidate try. Publication — preparation, the duplicate-name check, and the rename into place — stays outside the loop, so the retry covers the clone and only the clone. Expressing it as a loop rather than as an explicit first-and-second attempt is what makes "a fresh empty staging directory per attempt, removed on every exit path" a single statement instead of two that can drift apart.

Clone attempts run with the manager's own environment plus `GIT_TERMINAL_PROMPT=0`, and a batch-mode `GIT_SSH_COMMAND` when — and only when — nothing else has configured an SSH command. That environment is settled once, before the first attempt, and every attempt shares it. Nothing else in the manager changes environment: reading Git configuration, `marketplace list`, and dependency installation keep passing the manager's environment through by reference.

When every attempt fails and there was more than one, the reported error names both attempted sources and inlines both underlying messages, because the CLI surfaces `error.message` and a user looking at a failed private install needs to see that SSH was tried and how it went. Both failures survive as the failure's `cause`, following the existing `cause` use in name derivation — each as the object Git's runner threw, unless its own message quoted a credential, in which case a replacement carrying the sanitized message stands in for it.

### Decisions

- **Decision:** Retry on any clone failure, rather than only on a failure that looks like an authentication problem.
  - **Why:** The failure reason is not available to decide on. `runGit` flattens every Git failure into one message and discards the exit code, and Git's authentication stderr is localized and version-dependent, so recognizing "auth failure" means string-matching text that is free to change. A single unconditional retry costs one extra clone attempt in the case where the source is simply wrong, and that attempt fails without prompting.
  - **Alternatives considered:** Inspecting the exit code or matching stderr was rejected as a brittle test on text the project does not control. Retrying repeatedly, or on transports beyond SSH, was rejected — there is exactly one alternative spelling of an HTTP(S) source, so one retry exhausts the option.

- **Decision:** Derive the SSH source with `URL` parsing, and produce exactly one form: SCP `git@host:path`, taking nothing from the HTTP(S) authority but the host, and decoding percent-escapes in the path.
  - **Why:** `URL` decides what is HTTP(S) without a pattern of the project's own. SCP `git@host:path`, bare paths, and a Windows drive letter are rejected as a consequence of failing to parse at all; `ssh://`, `file://`, and `git://` parse perfectly well as `URL`s and are rejected by the one explicit protocol guard, so the only list to maintain is that guard's pair of HTTP(S) schemes. SCP syntax is what a user's `~/.ssh/config` and a forge's own instructions are written in. The escapes have to be decoded because Git decodes them in an `ssh://` URL but not in SCP syntax, so an undecoded `team/my%20repo.git` would ask the remote for a repository spelled exactly that; a malformed escape derives nothing, since attempting a source known to be wrong is worse than not retrying. Query and fragment are dropped because they are not part of the repository path.
  - **Alternatives considered:** Always emitting `ssh://` was rejected as the less recognizable of the two forms. Rewriting only the scheme, leaving `https://host/path` as `ssh://host/path`, was rejected — it drops the `git` user that every forge requires.

- **Decision:** Use `git` as the SSH user always, and carry neither the source's userinfo nor its port into the derived source. Supersedes an earlier decision on this branch to preserve the userinfo user and to emit `ssh://user@host:port/path` for a source carrying a port; both were wrong.
  - **Why:** A userinfo is an HTTP credential, not an SSH login. `https://<token>@github.com/owner/repository.git` is GitHub's own documented HTTPS form, so preserving the userinfo user transmits a live token to the remote as an SSH login name, where it lands in the server's authentication log and in any bastion's along the way — and it buys nothing, because the SSH login on GitHub, GitLab, Gitea, and Bitbucket Server is `git` whatever the HTTPS user was. An HTTP(S) port is not an SSH port either: `https://git.company.com:8443/team/tools.git` serves SSH on 22, so `ssh://git@git.company.com:8443/…` opens an SSH handshake against the HTTPS listener, which can only hang to a protocol timeout and then report a URL the user never typed. A password was always dropped and still is. With one output form there is no `ssh://` branch left to maintain.
  - **Alternatives considered:** Preserving a non-`git` user for an internal forge was rejected once it became clear the same rule forwards tokens; a user who needs another SSH login or a non-standard SSH port types that SSH source themselves, which costs them the shorthand only in the case where guessing would be unsafe.

- **Decision:** Disable Git's terminal prompt with `GIT_TERMINAL_PROMPT=0` and apply `GIT_SSH_COMMAND=ssh -o BatchMode=yes` — when no SSH command is configured at all — to *every* clone attempt, the first one included, settling that environment once before the loop starts. Supersedes an earlier decision on this branch that confined the batch-mode command to the derived SSH attempt.
  - **Why:** Without the prompt setting the fallback is unreachable in its main case: a private HTTPS clone with no credential blocks on a terminal prompt instead of failing, so the SSH attempt never runs. `GIT_TERMINAL_PROMPT=0` suppresses Git's own prompt and nothing else — credential helpers and `GIT_ASKPASS` still resolve credentials normally, which is why neither is touched here, and it has no Git-config equivalent to conflict with.

    Confining `BatchMode=yes` to the derived attempt looked right — the HTTP(S) attempt does not run SSH — and is wrong, because Git decides the transport after `tx` hands over the source. `git config --global url."git@github.com:".insteadOf https://github.com/` is an ordinary corporate and CI setup, and under it `tx marketplace add fx/tx` has its *first* clone rewritten to SSH. Against a host not yet in `known_hosts`, ssh(1) then asks `Are you sure you want to continue connecting…?` on `/dev/tty`, which `GIT_TERMINAL_PROMPT` does not govern — it governs Git's prompts, not ssh's. The command hangs, and the retry this change exists for never runs. An injected `GIT_SSH_COMMAND` is inert for a clone that really does speak HTTP(S), so applying it uniformly closes that hole for nothing. Settling the environment before the loop rather than per attempt also removes the per-candidate conditional and, because the environment-variable check short-circuits, keeps the configuration reads to at most one per addition. It is computed per addition rather than cached, because the manager's environment defaults to the live process environment.
  - **Alternatives considered:** Setting `GIT_ASKPASS` to a no-op was rejected — it would disable a credential helper the user deliberately configured, turning a working HTTPS install into a fallback to SSH. Leaving prompting alone was rejected: it makes the feature not work. Detecting `insteadOf` rules and applying batch mode only when one matches was rejected as reimplementing Git's URL rewriting to decide something a uniform environment settles for free.

- **Decision:** Treat `GIT_SSH_COMMAND`, `GIT_SSH`, and `core.sshCommand` as one question — is an SSH command configured — and inject nothing when any of them answers yes, reading `core.sshCommand` from command scope in the environment and from the global and system files, and from no other scope. Supersedes an earlier decision on this branch that checked `GIT_SSH_COMMAND` alone, a second that read `core.sshCommand` without restricting its scope, and a third that restricted it to the two files and so stopped seeing command scope.
  - **Why:** Git honours `GIT_SSH` as well as `GIT_SSH_COMMAND`, with the latter taking precedence, so injecting `GIT_SSH_COMMAND` bypasses a caller's `GIT_SSH` wrapper. `core.sshCommand` is worse: Git documents it as overridden by the environment variable, and pinning a deploy key with `git config --global core.sshCommand "ssh -i /run/secrets/deploy_key -o IdentitiesOnly=yes"` is the standard CI setup, with no `GIT_SSH_COMMAND` set anywhere. Injecting one there drops the `-i` and the SSH retry dies with `Permission denied (publickey)` — in exactly the deploy-key case this feature exists for.

    The scope matters as much as the variable, and it cuts both ways. A plain `git config --get core.sshCommand` reads the local configuration of whatever repository the user happens to be standing in, and `git clone` does not apply it: the clone creates the repository it writes into rather than joining that one. Verified on git 2.34.1 — a repository-local `core.sshCommand` reads back from `git config --get` while `GIT_TRACE=1 git clone` in the same directory traces a plain `ssh -o SendEnv=GIT_PROTOCOL …`. Reading that scope reports "configured" for a command the clone will never run, suppresses batch mode for nothing, and leaves the attempt to block on the host-key prompt the default exists to prevent. So the probe asks `--global` and then `--system`, two scoped reads rather than parsing `--show-scope`: they work on every Git version and have no output format to misread. A non-zero exit means unset in that scope, or a system file this process cannot read, and both mean the same thing here.

    Narrowing to those two files alone was itself too narrow, and it dropped a scope a clone does apply. `GIT_CONFIG_COUNT` with its `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>` entries (Git 2.31 and later) is the documented way to supply configuration without writing a file, it is *command* scope, and it outranks both files. Verified on git 2.34.1: with `core.sshCommand` supplied that way, `GIT_TRACE=1 git clone` traces the configured command, while `git config --global --get core.sshCommand` and the `--system` read both exit 1. A CI job that pins its deploy key like that would therefore have seen a batch-mode `GIT_SSH_COMMAND` injected over it — the environment variable wins over command-scope configuration — the key dropped, and the retry die with `Permission denied (publickey)`: the deploy-key case this feature exists for, broken by the fix that scoped the probe. So the environment is scanned first, before either file. It costs no Git call, it is the only route by which command scope can reach a clone whose argv this code builds itself, and unlike the local scope it is not tied to the repository the caller is standing in. Keys are compared case-insensitively, because Git's configuration section and variable names are; a `GIT_CONFIG_COUNT` that is not a whole number describes no entries and is scanned as none, a negative one scanning none because the scan starts at zero, and an entry whose value is empty or blank configures nothing, matching how the file scopes read a blank `git config --get`.

    A configured command is an arbitrary shell string rather than an argument vector, so appending an option to it is guessing at its structure; the user who set it owns its behavior, including a key whose passphrase prompt can still block.
  - **Alternatives considered:** Appending the option was rejected as invention. Overriding outright was rejected as breaking the case the retry exists to serve. Checking only the environment was rejected once `core.sshCommand` turned out to be the ordinary way of configuring a deploy key. Reading every scope at once was rejected once the local scope turned out to describe a command the clone cannot use; reading only the two configuration files was rejected in turn, once command scope in the environment turned out to describe one the clone does use.

- **Decision:** Let a staging removal that fails be ignored, rather than propagate, on the publication path as well as between clone attempts.
  - **Why:** Between attempts, propagating an `EACCES` on a partial checkout would replace the clone failure the user needs with a filesystem error, and would abandon the SSH retry that is the whole point of this change — while leaving the directory behind either way, so nothing is gained for what it costs. The publication path has the same shape and was initially left alone, which was an oversight: its removal runs in a `finally`, so when preparation, dependency installation, or the installed-name check throws, a refused removal rejects out of that `finally` and replaces the real failure. A user whose trusted lifecycle script failed would read a filesystem error about a directory they never asked about. Both paths now go through one helper.
  - **Alternatives considered:** Reporting both the clone failure and the cleanup failure was rejected as a message about `tx`'s internals in place of one about the user's repository.

- **Decision:** Export the staging-removal helper so its swallow is unit-tested directly, against a path whose parent is a regular file.
  - **Why:** The behavior under test is "a removal the filesystem refuses is not the failure", and it needs a refusal no environment can talk its way out of. The obvious trick — `chmod` the parent directory to `0o555` — only blocks a process that is not root, so under any plain `docker run … bun test`, a root devcontainer, or a self-hosted runner the removal succeeds, the branch stops being covered, and at a 100% gate the gate stops meaning anything there. A path whose parent is a regular file rejects with `ENOTDIR`, which `force: true` does not suppress — it suppresses `ENOENT` only — and `ENOTDIR` is a property of the path rather than of the process, so it reproduces identically for uid 0 and for everyone else. Testing it through the exported helper follows this module's existing convention: `runGit`, `normalizeMarketplaceRepository`, `deriveMarketplaceName`, and `deriveMarketplaceSshRepository` are all exported for direct testing.
  - **Alternatives considered:** Mocking `node:fs/promises` was rejected as testing the mock rather than the behavior. Keeping the permission-based test was rejected outright: a test that inverts on the privilege of whoever runs it reports an environment difference as a defect in one direction and covers nothing in the other.

- **Decision:** Report both attempts in one error whose `cause` is an `AggregateError` of both failures, rather than reporting only the last one or introducing an error class.
  - **Why:** Reporting only the SSH failure would tell the user their SSH attempt failed and hide that HTTPS was tried first, which is the context that makes the message actionable. The CLI surfaces `error.message`, so both underlying messages are inlined there; `AggregateError` keeps both failures for anything reading `cause`, each with its original stack unless its message carried a credential — a message that has to change takes a replacement error with it, because a stack repeats the message it was built from. Name derivation already attaches a `cause` to a wrapped error, so this extends an existing shape rather than adding a type.
  - **Alternatives considered:** A dedicated error class was rejected as surface with no reader. Discarding the HTTPS failure was rejected as losing the more informative of the two messages.

- **Decision:** When only one attempt was possible, rethrow its failure unchanged.
  - **Why:** Every non-HTTP(S) Git source — an `ssh://` URL, SCP syntax, `file://`, a bare path — gets exactly one attempt, and there is no second attempt to combine with. Wrapping a lone failure in a sentence about a retry that never happened would be a false statement about what tx did.
  - **Alternatives considered:** Wrapping uniformly was rejected for that reason.

- **Decision:** Compose the attempt names credential-free instead of scrubbing them, and scrub the quoted Git output by deleting the source's anchored userinfo runs — `userinfo@` and `user@`, both taken from the raw source string — and nothing else. Supersedes three earlier decisions on this branch: one that redacted only the two attempt names, one that removed literals taken from the parsed `URL` including the bare username, and one that substituted whole URL forms and removed the bare password as a safety net.
  - **Why:** Redacting the names alone leaves the leak in place, because the message inlines each underlying Git message and Git echoes the clone URL in its stderr with only the password stripped: `fatal: unable to access 'https://<token>@github.com/owner/repository.git/': …`. The CLI writes `error.message` to standard error, so the token reaches the terminal and the CI log through the quoted output rather than through the label. Removing literals taken from the parse fails on both counts: `URL` percent-encodes what it parses while Git is handed the raw string and echoes it back raw, so a password holding any character `URL` escapes — `@`, a space, `:`, `/`, `?`, `#` — yields literals that match nothing; and deleting the bare username rewrites unrelated text, since `git`, `me`, and `com` are all real HTTP(S) usernames, so `https://git:token@github.com/acme/tools.git` was reported as `hub.com/acme/tools.`, a repository nobody typed.

    Enumerating whole URL forms — the source as handed over, the source with its password dropped — was the next attempt, and it fails too, in both directions. It **misses a real Git output form**: a source with a username and no password leaves Git asking for the password, and with `GIT_TERMINAL_PROMPT=0` it aborts naming the credential through `credential_describe`, which omits the path unless `credential.useHttpPath` is set. The output is `fatal: could not read Password for 'https://<token>@github.com': terminal prompts disabled` — host-only, so neither whole-URL literal matches, and the live token reaches standard error and the attached cause. That is precisely the token-in-the-username-position case this change names as its motivation, and every fixture used a `user:password@` source, so nothing covered it. And the bare-password safety net **corrupts the diagnostics**: `https://user:tools@github.com/acme/tools.git` reported `unable to access 'https://github.com/acme/.git/'` in both quoted messages, naming repositories that do not exist, because the password is an ordinary word the repository name also spells. A password reusing an org, a repository, or a word like `tools`, `main`, or `dev` is the collision case, and it is not rare.

    Both mistakes come from describing the *container* rather than the credential. Git only ever spells a credential as a `userinfo@host` run, and it spells it that way in every shape it prints — the URL it was handed, the URL it echoes with the password stripped, and the host-only form above. So the scrub matches the userinfo run *including its trailing `@`* and deletes it, in exactly two spellings taken from the raw source string: `userinfo@`, and `user@` for the form Git prints after dropping the password. There is no URL shape left to enumerate and no bare secret left to remove. The `@` is what makes each literal safe, because host and path text carries none; and deleting `userinfo@` from `https://user:pass@host/path` already leaves `https://host/path`, so the whole-URL substitution bought nothing this does not. Reading the userinfo from the raw string rather than from the parse — the authority between `://` and the first `/`, `?`, or `#`, its userinfo everything before the last `@` — keeps the literal spelled exactly as Git will spell it.

    The names stay built rather than repaired — the source parsed, its userinfo cleared, its `href` taken — and are composed after the Git output is scrubbed, which puts every name out of reach of every deletion. The derived SSH candidate is `git@host:path` and carries no credential at all, which is why nothing scrubs it.

    Each literal is emitted only when the component it is built from is non-empty, so a degenerate one is never produced. `https://:token@host/path` — an empty user with the token as the password — is a form GitHub and GitLab both accept, and its `user@` run would be the bare string `@`: deleting that takes every `@` out of Git's output, so `git@github.com` reads back as `gitgithub.com`, a host that does not exist, in the composed message and in both attached causes. The same goes for a wholly empty userinfo, `https://@host/path`, which yields no literal at all. Nothing is lost by the guard: the run Git quotes for the first form is `:token@`, the whole userinfo, and a password-stripped `https://@host/path` holds no credential left to remove.

    Two losses are accepted, and documented rather than papered over. A userinfo *user* quoted without its `@`, such as a server message naming the account, survives; removing a bare identifier is what fabricates sources, and the password is covered regardless, because Git never spells one outside a userinfo run. And when the source's user is literally `git` — real on Gitea and for GitLab deploy tokens — deleting `git@` also takes it out of Git's own quoted SSH output, so `git@host:path` reads back as `host:path`. That is cosmetic, confined to text Git quoted, and the reported SSH name is composed separately and stays exact.
  - **Alternatives considered:** Reporting the sources verbatim was rejected as leaking a credential the user handed to a clone, not to a log. Omitting the sources from the message was rejected — naming what was tried is the point of the message. Leaving the cause errors unsanitized was rejected: an error whose own message repeats the token is the same leak one dereference away. An error whose message has to change is replaced rather than edited in place, because its stack repeats its message; an error with nothing to remove is kept exactly as Git's runner threw it. Keeping the bare-password rule alongside the anchored runs was rejected: it can only fire where a userinfo run did not, which by Git's own output is nowhere, and its only demonstrated effect was corrupting repository names.

### Non-Goals

- A `--ssh` or `--no-fallback` flag. The fallback needs no input from the user, and [0008](./0008-link-local-marketplace-sources.md) already rejected an equivalent `--link` flag as more surface for the same outcome.
- Progress or status output while the fallback runs. Telling the user "HTTPS failed, retrying over SSH" requires threading a reporter into `MarketplaceManager`, which has none today. The combined failure already names both attempts once the outcome is known.
- Credential storage, credential helpers, token authentication, and askpass implementations. This change configures none of them and disables none of them.
- Applying the fallback to `marketplace update`, or converting an already-installed clone's remote from HTTPS to SSH. A marketplace installed through the fallback records the SSH remote at add time because that is what it was cloned from; nothing rewrites an existing one.
- Local directory sources. Classification and the reference path are untouched, and a local source never reaches a clone.
- Timeouts on Git operations, per [PR Review](../../REVIEW.md).
- Any change to `src/`. The whole change lives in the marketplace plugin.

## Open Questions

- [ ] Should the fallback report its attempts as they happen rather than only in the combined failure? It needs a reporter in `MarketplaceManager` first, which no other behavior there wants yet.
- [ ] Should `marketplace add` offer to convert an installed clone's remote, or apply the fallback when a marketplace is updated? Neither has a command to hang off today.
- [ ] Should a source that already fails HTTPS authentication be remembered, so a later addition against the same host starts with SSH? Not worth a persisted preference for a retry that costs one failed connection.
- [x] Should the marketplace plugin's ad-hoc Git-source parsers be unified behind one `parseGitSource`? `carriesGitSyntax` and `deriveMarketplaceName` predate this change and the SSH derivation joins them, each reading the same source with its own rules. It is a refactor of existing architecture rather than a defect this change introduced, so it is recorded rather than done here. **Settled by [0014](./0014-pin-marketplace-versions.md): no, not as one parser — the *rule* is unified instead.** The one thing they genuinely shared, where a source's authority begins and ends, is now a single function in `plugins/marketplace/source.ts` that classification and the version suffix both read, which is what kept them from disagreeing about which `@` is a login. Name derivation and SSH derivation are left alone: they answer different questions with different contracts — what a source is called, and how else it can be reached — so folding them in would produce one function with three result shapes and three sets of edge cases, which is not a unification of anything.
